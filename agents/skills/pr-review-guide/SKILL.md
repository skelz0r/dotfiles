# PR review guide

A page that lets a reviewer understand a large pull request without reading
it top to bottom: what it ships, what can be skimmed, how one real case
flows through the change, where the hand-written code lives, what keeps it
true, and how to read the commits. The PR description stays an executive
summary and links to the guide.

Output, generated by one script from one markdown file:

```
~/share/<slug>/
  GUIDE.md      single source of truth, the only file ever edited
  build.py      renders GUIDE.md with pandoc, resolves and verifies links
  style.css     tokens derived from the project's identity + components
  img/          screenshots of the real application
  index.html    generated, never edited by hand
```

Skill assets (in this skill's base directory): `assets/GUIDE.md` (skeleton
with the five tabs), `assets/build.py`, `assets/style.css`, and
`references/content.md` (how to collect each fact, what each tab holds),
`references/theming.md`. Read the `upload-assets` skill's
`references/static-pages.md` first: where the files live, how to find the
project's identity, look at the page and publish it, shared with other
skills that publish a static page.

## Workflow

### 1. Frame

Confirm with the user, in one AskUserQuestion round if anything is unclear:

- **The PR** and its audience (reviewers of the team, another team, both).
- **The language** of the guide: the user's.
- **The end-to-end case**: one real case that crosses most layers of the
  change. Propose the one you would pick and why.
- **The slug** (`<project>-pr-<n>`) and the working directory.

### 2. Collect the facts

Follow `references/content.md`: pinned commit, numbers of the diff split
between generated, mechanical and hand-written code, the files and methods
to link, real payloads produced by running the code, real failure messages,
screenshots. Read the commit messages: they often hold the why the guide
needs.

### 3. Theme

Follow `references/theming.md`: detect the project's identity and set the
tokens at the top of `style.css`.

### 4. Scaffold

As described in `static-pages.md`, with `img/` for the screenshots:

```bash
mkdir -p ~/share/<slug>/img
cp <skill>/assets/{GUIDE.md,build.py,style.css} ~/share/<slug>/
ln -s ~/share/<slug> <working-dir>/sandbox/<slug>
```

### 5. Write `GUIDE.md`

Fill the front matter (`repo`, full `sha`, `pr`, `checkout` pointing at the
local clone so links are verified), then the intro and the five tabs of the
skeleton. Link with the schemes `build.py` resolves at the pinned commit:
`gh:path#L10-L20`, `tree:path`, `commit:<sha>`, `pr:`. Components:
`::: callout` (`.info`, `.good`, `.warning`; a first paragraph made only of
bold text becomes its title), `[503]{.status}` badges (cells of a table
column headed "Statut", "Status" or "HTTP" get one too), tables, fenced code
with a language (`ruby`, `json`, `yaml`, `http`, `bash`). Links and comments
inside code are left alone: `build.py` works on pandoc's syntax tree.

### 6. Build and check

```bash
cd ~/share/<slug> && python3 build.py
```

Zero warnings: every `gh:` path exists at the pinned commit with the right
type (file or directory), line anchors are within the file, commits belong
to the branch, no GitHub link is pinned to a branch name, no table row is
split by a stray `|`, no link is left unresolved, every `#anchor` exists,
no id is duplicated, every image exists.

Then look at every tab as described in `static-pages.md`.

### 7. Publish

Before the upload, `python3 build.py --check-urls` (every external link
answers 200). Then publish as described in `static-pages.md`, into `<slug>`
with `--except build.py --except GUIDE.md`, and offer to add the URL to the
PR description.

### 8. Iterate

Always in `GUIDE.md`, then rebuild and republish to the same folder. When
the branch moves, bump `sha` and reread what changed.

## Guidelines

These come from iterations on a real guide; each was a correction.

- **Executive first, detail behind tabs.** The intro and the overview tab
  answer "what is this PR and what must I read"; everything else is one
  click away. Tabs follow the reader's questions, not the file tree.
- **Say what can be skipped, with numbers.** Generated and mechanical files
  are most of a large diff; quantify them from `git diff --numstat` and say
  which check guarantees them, so the reader trusts skipping them.
- **One real end-to-end case.** Follow a single real case through every
  layer rather than listing layers in the abstract. Each step's title says
  what the reader is looking at, and its first sentence says how it differs
  from the previous one: a title like "what the API returns in production"
  left the reader lost between the catalogue of what can happen and what
  actually happens.
- **Only real artefacts.** Code excerpts, payloads, generated
  documentation, failure messages and screenshots all come from the pinned
  commit or from running it. Truncate visibly with `…`. Never invent a
  payload: a plausible fake misleads the reviewer the guide is for.
- **Link everything, pinned.** Files on the method that matters
  (`gh:…#L43`), directories with `tree:`, commits to their page in the PR.
  Never link a branch name: the guide outlives the branch.
- **Label assumptions as assumptions.** A decision that rests on a belief
  ("nobody relies on these codes") is stated as a hypothesis, with why it
  is believed and who adapts if it is wrong, in a `warning` callout.
- **Behaviour changes in a Before / After / Why table**, so a reviewer
  can check each one against the code.
- **Show the real failure messages** of the safety nets: they tell a
  future contributor what to do better than any description.
- **Readable code.** Code blocks are dark and highlighted, inline code
  stays light, a link set on code must still look like a link, a table
  cell never contains a `|`, even inside backticks.
- **Screenshots of the real UI, cropped to the block discussed.** Look at
  each one before using it: a screenshot of the change often exposes a bug
  in the change itself, fix it rather than publish it.
- **Numbers come from commands.** Operation counts, file counts, line
  counts: computed on the pinned commit, identical wherever they appear.
- **The only script switches tabs** and keeps `#anchors` working; without
  it every tab is shown. Highlighting is done at build time by pandoc.
