# Decision mockups

Static mockups that put each option of a decision under the reader's eyes,
from the real entry point to the real end, and say on each screen what is
good and what is weak about it. The goal is a decision, not a design: the
mockups are as simple as the argument allows.

Output, generated by one Python script (stdlib only):

```
~/share/<slug>/
  build.py        single source of truth, the only file ever edited
  style.css       layout + tokens derived from the project's identity
  MOCKUPS.md      iteration rule, options, conventions, what is not shown
  index.html      decision, option cards, criteria matrix, reading guide
  option-1/1-….html, 2-….html, aside.html
  option-2/…
```

Skill assets (in this skill's base directory): `assets/build.py` (template
with a small worked example to replace), `assets/style.css`,
`assets/MOCKUPS.md`, and `references/theming.md`. Read the `upload-assets`
skill's `references/static-pages.md` first: where the files live, how to
find the project's identity, look at the pages and publish them, shared
with other skills that publish a static page.

## Where it helps

- Several UX flows for one need: consent, onboarding, signup, recovery.
- Integration between services: who owns which screen, where the user is
  redirected, who holds the proof (e.g. submission on our side vs on a
  partner's side, embedded signature link, API submission).
- API contract choices: one option per contract, screens are HTTP exchanges
  and the client code that calls them, annotations on errors and breaking
  changes.
- Migration or rollout strategies: the sequence of emails, admin screens
  and scripts each strategy implies.
- Internal tooling choices: batch validation by CSV, by script, by endpoint.
- Notification or email variants, empty and error states, permission
  models seen by each role.
- Material for a meeting with another team: the mockups make the cost each
  option asks of them visible.

Not for: a single design to polish (use frontend-design), or a choice with
no visible or tangible difference between options.

## Workflow

### 1. Frame the decision

From the source document, extract and confirm with the user
(AskUserQuestion when anything is ambiguous, one round, up to 4 questions):

- **The decision point**: one sentence, "they only differ on X". Everything
  else is invariant and must be identical across options.
- **The options**: 2 to 5. A variant of an option is its own option
  (`2a`, `2b`) rather than a branch inside one walkthrough.
- **The actors**: every service or party that displays a screen.
- **The entry point and the end**: the email, link or event that starts
  the flow, the screen where it stops.
- **Existing screens to copy**: screenshots or URLs of pages that already
  exist. Reusing a real page unchanged is an argument in itself.
- **The criteria** for the matrix: screens count is automatic; add what the
  decision actually hinges on (breaks in the flow, work asked of each team,
  who holds the proof, risks, delay).
- **Exact domain vocabulary**: states and verbs (submitted is not
  validated). Wrong words discredit the whole mockup.
- **The slug** and the working directory of the topic.

### 2. Theme

Follow `references/theming.md`: detect the project's identity, map it to
the tokens at the top of `style.css`, set `LOGO` and `ACTORS` in
`build.py`.

### 3. Scaffold

As described in `static-pages.md`:

```bash
mkdir -p ~/share/<slug>
cp <skill>/assets/{build.py,style.css,MOCKUPS.md} ~/share/<slug>/
ln -s ~/share/<slug> <working-dir>/mockups
```

### 4. Write `build.py`

Replace the worked example entirely:

- **Constants**: fictional data in one block (see guidelines), `TITLE`,
  `INTRO`, `LABELS` in the mockups' language, `ACTORS`, `OPTIONS`,
  `CRITERIA`, `NOT_SHOWN`.
- **Shared screens**: one function per shared screen, taking the
  walkthrough and what varies (the next link, the action buttons, the
  extra notes). Shared building blocks (a summary card, a form) are
  fragment functions returning HTML.
- **One function per option**: `w = Walkthrough("option-1")`, then
  `w.screen(name, title=, actor=, body=, notes=[...])` in order, and
  `w.aside(...)` for an off-path screen (a failure case reached by a
  secondary button such as "Et si l'agent se trompe de compte ?").
  Numbering and "écran N sur M" are automatic.
- **Non-UI screens**: `mail()`, `http()`, `terminal()`, `sequence()`,
  `code()` fragments; set `narrow=False` for wide content.
- **Markers**: `m(n, kind)` in the body, matching the n-th note and its
  kind. The build warns on mismatches and broken links.

### 5. Build and check

```bash
cd ~/share/<slug> && python3 build.py
```

Zero warnings. Then look at the index and at least one screen per option
as described in `static-pages.md`.

### 6. Write `MOCKUPS.md`

From `assets/MOCKUPS.md`: the iteration rule, the options table, the
screens copied from existing pages, the reading conventions, and what the
mockups deliberately do not show, with why.

### 7. Iterate

Always in `build.py`, then rebuild. When the user removes something, move
it to `NOT_SHOWN` and `MOCKUPS.md` if a reader could expect it.

### 8. Offer to publish

Propose to publish as described in `static-pages.md`, into a folder
chosen by the user, with `--except build.py --except MOCKUPS.md`. Check the
fictional data one last time before the upload.

## Guidelines

These come from iterations on real decision mockups; each was a correction.

- **Linear walkthroughs, no branching.** Each option runs from the entry
  point to the end in one straight line. A choice inside a walkthrough is a
  sign of two options. Failure cases are off-path asides, linked from the
  screen where they happen.
- **Invariant screens are strictly identical.** Only the part the decision
  touches changes (often just the action buttons at the bottom of a shared
  screen). The reader must see where options diverge, not hunt for it.
- **Copy existing screens rather than invent.** Reproduce the real page
  from a screenshot or URL, block by block, and annotate the only things
  added or removed. "No new page to draw" is a strength worth a note.
- **Make actor changes visible.** One header style per actor and a "Vous
  êtes sur X" strip. When this differs from reality (the partner's real
  header is white), say so in the reading guide.
- **Annotations in the margin, never in the UI.** No warning boxes inside
  the screens: they pollute the mockup and hide what the user would really
  see. Numbered markers in the screen point to notes in the sidebar, of
  three kinds: `info` (a fact), `good` (a strength), `weak` (a weakness).
- **Weaknesses of the preferred option are annotated too.** The
  recommendation shows on the index (green card and matrix column), never
  by hiding its costs.
- **Show only what exists or is being decided.** Features that do not
  exist (a PDF export no one generates) or that are identical in every
  option (a prefill orthogonal to the decision) are removed and listed
  under "what the mockups do not show". Simpler beats complete.
- **Fictional data from the first draft.** Organisation, identifiers,
  people, emails, phone numbers: invented, in one constants block,
  obviously fake (`Saint-Exemple`, `12345678900012`, `exemple.fr`). Only
  the real subject of the decision keeps its real name. Say it on the
  first screen ("Ceci est un exemple") and in the footer.
- **Exact vocabulary.** Use the domain's states and verbs as the system
  defines them; a confirmation screen says what really happened.

## Writing annotations

- Title: the claim, in a few words ("Le retour n'est pas garanti").
- Body: one or two sentences of evidence, as concrete as possible: an
  endpoint (`POST /api/v1/demandes`), a number from the data ("29 adresses
  couvrent 128 SIRET"), a ticket, a validation rule, who must build what.
- One idea per note; 1 to 5 notes per screen. A screen with nothing to
  say needs no note.
- Put the note on the screen where the reader would experience the point,
  and the marker on the element concerned (a button, a field, a header).
- Write for the other team too: the mockups often end up in front of the
  people each option asks work from.

## Index

- The decision in one or two sentences, the invariant stated explicitly.
- One card per option: screens count and where the decisive step happens,
  scenario, what it requires and from whom, recommended option(s) flagged
  with `reco`.
- The criteria matrix: short cells qualified `good`, `weak` or `info`,
  same wording as the annotations they summarise.
- The reading guide (generated) and what is not shown.
